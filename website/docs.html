The conversation layer, explained.

This guide covers installation inside the Salesforce org, the message path through the Meta Cloud API, template and consent handling, routing, and the security model. It is written for the admin who has to make it work on a real org.

Install and connect

  1. Install the managed package or deploy the LWC bundle into the target org.
  2. Create a Meta app with the WhatsApp product and a phone number ID.
  3. Store the system user token, phone number ID and webhook verify token in Salesforce protected metadata or a Named Credential.
  4. Register the Salesforce site URL as the Meta webhook callback and subscribe to the message fields you use.
  5. Assign the permission set to admins, agents and the integration user.

The package does not ask for a middleware endpoint. The Apex callout layer signs and sends requests directly to the Meta Cloud API; inbound webhooks are verified and processed in the org.

Keep the token out of page markup and client-side JavaScript. A Named Credential or protected custom setting keeps it server-side and rotatable without a code deploy.

Message path

Outbound

An agent sends from the conversation component. The server checks the record, consent and template rules, then calls the Cloud API. The provider response is stored on the message record with the provider message ID, status and failure reason.

Inbound

Meta posts to the webhook. The handler verifies the signature and verify token, dedupes on the provider message ID, resolves the phone number to a Salesforce record, and writes the message before returning 200. A failed write returns a non-2xx so the provider retries instead of silently dropping the message.

Statuses (sent, delivered, read, failed) are applied to the same record. Media is downloaded server-side and stored according to the org's file policy, not by URL forwarding to the browser.

Templates

Templates are built and validated in the org before submission. The builder checks category, header, body variables, buttons and media handle requirements, then sends the template to Meta for approval. Status is polled or refreshed by an admin action.

  • Authentication templates are restricted to one-time codes.
  • Utility templates cover order, account and appointment updates.
  • Marketing templates require an explicit marketing opt-in.
  • Variables must match the submitted sample; changing the body creates a new version.

Consent

Consent is stored on the record that owns the relationship, not in a parallel table. The record keeps the opt-in state, the source, the proof (form version, timestamp and page) and the scope (transactional or marketing).

Outbound sends are checked server-side. An agent cannot bypass a missing marketing opt-in by sending a marketing template manually. Opt-outs are applied immediately and preserved as part of the record history.

Routing and cases

Inbound conversations map to any Salesforce object through a configurable resolver: phone field on Lead, Contact, Account or a custom object. Unmatched numbers can create a Lead, open a Case or land in an unassigned queue.

Routing rules assign owners and queues using standard Salesforce ownership. Case creation uses the org's record types, assignment rules and escalation rules, so existing service processes still apply.

Security and data

  • Webhook requests are verified before any record is written.
  • Outbound credentials live in protected metadata or Named Credentials, never in the browser.
  • Sharing follows org-wide defaults, roles and permission sets. The package does not bypass sharing with without sharing for customer data.
  • Message bodies and media stay in the org according to your file and retention policy.
  • Every send is attributable to a Salesforce user or the integration user, with the provider response retained.

No second data store is introduced. There is no external middleware database holding conversation content, and no separate consent ledger outside Salesforce.

Limits and support

Throughput is bounded by Salesforce callout limits, Meta messaging tiers and your contract. Bulk sends should run through a queueable or batch job with retry and backoff, not a synchronous loop.
